## 1. Next shift

When dispatch has scheduled the driver, the Trip tab shows the **next shift**: route, bus, date and time. If there's nothing scheduled, it shows **Standby**.

The app gets this from `GET /api/v1/driver/trip`, the main call behind the Trip tab. It returns the current trip (if any), the next shift, and whether the driver is allowed to start.

## 2. Start trip

The driver presses and holds **Start trip**. Holding (instead of tapping) stops it from starting by accident in a pocket. The app asks for location permission the first time.

The app calls `POST /api/v1/driver/assignments/{id}/start`. On the server, `app/Actions/Trips/StartTrip.php` checks:

- the shift belongs to this driver
- it's no more than a few minutes before the shift starts, and the shift hasn't ended
- the bus and the driver don't already have a trip running
- the route is active, the bus didn't fail inspection, and the driver isn't suspended
- the bus has an **online kiosk** (see [Kiosk setup](/admin/kiosk-setup))

If any check fails, the server sends back a plain message, and the app shows it. If everything passes, the server creates the trip, marks the shift **Active**, the bus **On Route** and the driver **On trip**, and records arrival at the first stop.

## 3. Stops

The big green button at the bottom always shows the **one next thing to do**:

- **Depart (stop name)** when leaving a stop → `PATCH /api/v1/driver/trips/{id}/depart`
- **Arrive at (next stop)** when reaching it → `PATCH /api/v1/driver/trips/{id}/arrive`
- **Undo** takes back the last tap if it was a mistake → `PATCH .../undo`

:phone-shots{:shots='[{"src":"/images/driver/07-arrival-recorded.webp","caption":"Arrival recorded"}]'}

These times matter. The passenger tracker uses them to estimate when the bus will reach each stop, and the server learns travel times from them overnight.

The header shows whether the bus is on time, how many passengers are on board (from the kiosk), and the GPS state.

## 4. GPS

During a trip, `TripLocationService` runs in the background with a notification, so Android doesn't stop it. It sends the position to `PATCH /api/v1/driver/trips/{id}/location`:

- about **every 5 seconds** while the bus is moving
- **every 60 seconds** while parked, so monitoring knows the bus is stopped, not lost
- inaccurate readings (worse than 100 m) are dropped

These rules are in `location/GpsSendPolicy.kt`, and they match the web driver page exactly.

## 5. SOS and reports

During a trip the driver can press **SOS** (`POST .../sos`) or **report a problem** (`POST .../report`). Both show up right away on the admin's [live monitoring](/admin/daily-operations) page.

## 6. End trip, next leg, end shift

At the last stop, after marking the arrival, the button becomes **Hold to end trip** (`PATCH .../end`). The server closes the trip and marks anyone still on board as off the bus. The app shows a short summary.

:phone-shots{:shots='[{"src":"/images/driver/08-trip-completed.webp","caption":"Trip completed"}]'}

Then the driver chooses:

- **Start next leg**: run the return route on the same shift. This goes through the same start checks.
- **End shift**: done for the day (`POST /api/v1/driver/assignments/{id}/end-shift`). The bus and driver are freed.

If the driver forgets to end the shift, the server closes it after the shift's end time (`assignments:complete-expired-shifts`, every 15 minutes).

## When there's no signal

Buses pass through dead zones, so the app is built to keep going without signal. Every item it can't send is saved in a small database on the phone (SQLite) and sent later, oldest first.

| What | Without signal |
| --- | --- |
| GPS positions | Saved and sent later. The driver never sees an error. |
| Depart / Arrive / Undo | Saved and sent later. The button responds right away. |
| Start trip | If the server can't be reached, the app offers **Start offline trip**. The trip runs on the phone and is sent with its real start time once the signal is back (`POST .../offline-start`). The server marks it "recorded offline". |
| End trip | Ends on the phone and is sent later. |
| SOS, report | Need signal. |

To stop things piling up, only one round trip (two legs) can wait to be sent. A third offline start is refused until the older ones are sent.

If the server rejects something outright (for example the shift was cancelled meanwhile), the app sets it aside and tells the driver to contact dispatch instead of retrying forever.

Code: `data/OfflineDriverRepository.kt` (queues for trips the server knows about) and `data/OfflineTripRepository.kt` (trips started offline).
