The web app has **two separate APIs**. Don't mix them up.

| API | Address | Used by | Defined in |
| --- | --- | --- | --- |
| **App API** | `/api/v1` | Our own driver app and kiosk, and passenger browsing | `routes/api.php` |
| **Partner API** | `/api/platform/v1` | Outside developers, with an API key from `/developers` | `routes/platform.php` |

This page covers the **App API**. The Partner API is described in `libresakay-full/docs/platform_api_openapi.yaml`.

Controllers for the App API are in `app/Http/Controllers/Api/V1/`. They call the same actions as the web pages (for example `StartTrip`, `RecordPassengerTap`), so the rules are the same whether a driver uses the app or the website.

## How the apps sign in

Every call (except signing in and enrolling) sends a key in the header: `Authorization: Bearer <token>`. These are Laravel Sanctum tokens. Each one has a limited set of rights:

| App | How it gets the token | What the token allows |
| --- | --- | --- |
| Driver app | Bataeño Pass sign-in, then `POST /driver/auth/bataeno-pass` | `/driver/*` only |
| Kiosk | Enrollment code, then `POST /kiosk/enroll` | Its own trip, and posting taps |

A `401` response means the token is no longer valid. The driver app sends the driver back to sign in. The kiosk goes back to the enrollment screen but **keeps its unsent taps**.

`DELETE /auth/token` signs a device out.

## Kiosk endpoints

All paths start with `/api/v1`.

| Call | What it does |
| --- | --- |
| `POST kiosk/enroll` | Trade a one-time code for a kiosk token |
| `POST kiosk/heartbeat` | "I'm alive", every 60 seconds |
| `GET kiosk/config` | Settings the server can change remotely |
| `GET kiosk/credential-list` | Known passes, for checking passes without signal |
| `GET scanner/active-trip` | Which trip this kiosk's bus is running, if any |
| `POST scanner/taps` | Upload one tap (board or get off) |

## Driver endpoints

All paths start with `/api/v1/driver`.

| Call | What it does |
| --- | --- |
| `POST auth/bataeno-pass` | Sign in |
| `GET trip` | Everything the Trip tab shows: current trip, next shift, whether Start is allowed |
| `GET config` | App settings, including the live update server details |
| `GET schedule` | Upcoming shifts |
| `GET trips`, `GET trips/{id}` | Trip history and one trip's recap |
| `POST assignments/{id}/start` | Start a trip |
| `POST assignments/{id}/offline-start` | Send a trip that was started without signal |
| `PATCH trips/{id}/depart`, `arrive`, `undo` | Stop buttons |
| `PATCH trips/{id}/location` | GPS position |
| `PATCH trips/{id}/end` | End a trip |
| `POST assignments/{id}/end-shift` | End the shift |
| `POST trips/{id}/sos`, `sos/cancel`, `report` | Emergency and problem reports |
| `GET messages`, `POST messages/{id}/messages` and others | Messaging with dispatch |
| `GET charging`, `POST charging/start`, `charging/stop` | Record when an electric bus is charging |
| `POST device-token` | Register the phone for push notifications (Firebase) |

## Passenger endpoints

Under `/api/v1/passenger/`. Routes, stops, arrival times, schedules, announcements and trip planning can be read without signing in. A passenger's own data (ride history, saved trips, linking a card, alerts) needs a passenger token.

## Live updates

The server pushes changes over a live connection using **Reverb**, Laravel's WebSocket server. The apps use the same protocol as Pusher. Channels are defined in `routes/channels.php`:

| Channel | Who can listen | What comes through |
| --- | --- | --- |
| `route.{id}` | Anyone (public on purpose) | Bus positions and counts for one route |
| `trip.{id}` | That trip's driver, and kiosks on that bus | Taps and changes for one trip |
| `driver.{id}` | That driver | Shift changes, kiosk online/offline |
| `conversation.{id}` | People in that chat | New messages |
| `admin.operations` | Staff with live monitoring access | Everything the live map needs |

To join a private channel, an app first calls `POST /api/v1/broadcasting/auth` with its token.

If the live connection drops, the apps keep working by asking the server again on a timer, so live updates make things faster but aren't required.

## Limits

Each group of calls has a rate limit (for example sign-in is 6 per minute, and taps and GPS have their own limits). The limits are named in `routes/api.php` and set in `app/Providers/AppServiceProvider.php`. A `429` response comes with a `Retry-After` header saying how long to wait.
